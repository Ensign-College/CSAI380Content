## Purpose:

This week's project installs Airflow and builds your pipeline; this exercise makes sure you actually understand the moving parts before you depend on them. Starting from a DAG whose transform and load phases are already written, you will implement the extraction phase, modify the transform phase to see its effect, and reconfigure the Airflow you install through its Helm values — the IaC way, not by clicking. The data comes from your own STEDI application: its simulator generates the user signup events your pipeline extracts.

You will also provision the object storage your pipeline reads from using Terraform, and add a CI check so a broken DAG never reaches your cluster.

### Part One: Provision Object Storage with Terraform

1. On a new branch (`etl-practice`), add a Terraform resource to your `terraform/` directory that creates a **Google Cloud Storage bucket** for raw data (provided as [starter/terraform/gcs-bucket.tf](starter/terraform/gcs-bucket.tf)). The same file grants the Airflow pods in your namespace read and write access to that bucket through GKE Workload Identity, so your DAG can read the CSV and Airflow can store task logs there without any key. The binding covers the namespace named by your `student_name` variable, so install Airflow into that same namespace. Run `terraform plan` and `terraform apply`, and commit the configuration. Then confirm the binding exists:

   ```bash
   gcloud storage buckets get-iam-policy gs://<your-bucket> --format='value(bindings)' | grep 'namespace/<your-namespace>'
   ```

   No output means Airflow's pods (including `airflow-worker`) cannot read the bucket and the extract task will fail with a 403. Re-run `terraform apply` and read its error; if it says you lack `storage.buckets.setIamPolicy`, send that error to your instructor.

2. Upload the [country-codes CSV file](https://github.com/datasets/country-codes/blob/main/data/country-codes.csv) to your bucket using `gsutil cp` or the console. This is your extraction source.

### Part Two: Implement the Extraction Phase

3. Copy the pre-configured ETL DAG at [starter/dags/etl_pipeline.py](starter/dags/etl_pipeline.py) into your repository as `dags/etl_pipeline.py`. The transform and load phases are written; the **extract phase is a stub** marked `# TODO(student)`.

4. Implement the extract step as a Python Airflow task that:
   1. Reads the country-codes CSV from your GCS bucket.
   2. Reads simulated user signup events (JSON) from Redis. These come from the **STEDI simulator**, which you run in your namespace first:
      1. Read [Simulator (demo data)](https://github.com/STEDI-Balance/stedi-web#simulator-demo-data) in the stedi-web README to see what the simulator produces. If your copy of stedi-web is from before October 2026, download it again and let your 1.5 workflow rebuild and push your STEDI image.
      2. Copy [starter/k8s/stedi-simulator.yaml](starter/k8s/stedi-simulator.yaml) into your repository as `k8s/stedi-simulator.yaml`, replace `<stedi-image>` with your STEDI image, and apply it to your namespace. It runs STEDI with `SIMULATION=true` and its own Redis.
      3. Confirm the signup events exist: `kubectl exec deploy/stedi-simulator -c redis -n <your-namespace> -- redis-cli --scan --pattern 'signup:*'` lists 29 keys, and `redis-cli get` on one shows JSON with `user_id` and `country_dial_code`.
      4. In the DAG, `REDIS_CONN_HOST` already points at the simulator's Redis (`stedi-simulator.<your-namespace>.svc.cluster.local`, port 6379, no password). Read every key matching `signup:*`.
   3. Passes both onward to the transform step.

5. Install Airflow and run the DAG:
   1. Copy [starter/helm/airflow-values.yaml](starter/helm/airflow-values.yaml) to `helm/airflow-values.yaml`. Set `dags.gitSync.repo` to your course repository, and set `remote_base_log_folder` to your bucket from step 1. Commit and push your DAG first: Airflow loads it from GitHub.
   2. Check that your account can grant the permissions Airflow's chart needs. The chart creates an `airflow-pod-launcher-role` so the scheduler can start a pod for each task, and Kubernetes only lets you create a Role whose permissions you already hold. Every line must print `yes`:

      ```bash
      while read -r verb resource; do
        echo "$verb $resource: $(kubectl auth can-i "$verb" "$resource" -n <your-namespace>)"
      done <<'END'
      create pods
      get pods
      list pods
      watch pods
      patch pods
      delete pods
      create pods/exec
      get pods/exec
      get pods/log
      list events
      watch events
      END
      ```

      If any line prints `no`, stop and send the output to your instructor: your lab account is missing GKE permissions, and nothing in your values file can fix it. Installing anyway fails with `roles.rbac.authorization.k8s.io "airflow-pod-launcher-role" is forbidden: ... is attempting to grant RBAC permissions not currently held`. If you already hit that error, run `helm uninstall airflow -n <your-namespace>` once your instructor has fixed the permissions, then install again.
   3. Install it (this takes several minutes):

      ```bash
      helm repo add apache-airflow https://airflow.apache.org
      helm upgrade --install airflow apache-airflow/airflow -n <your-namespace> -f helm/airflow-values.yaml --timeout 15m
      kubectl get pods -n <your-namespace> -w   # wait until airflow-api-server, -scheduler, and -dag-processor are Running and ready
      ```

   4. Let Airflow reach MySQL: copy [starter/k8s/stateful/mysql-service.yaml](starter/k8s/stateful/mysql-service.yaml) into your `k8s/` directory and apply it, which gives MySQL the address `mysql.<your-namespace>.svc.cluster.local`.
   5. Open the UI with `kubectl port-forward svc/airflow-api-server 8080:8080 -n <your-namespace>`, go to `http://localhost:8080`, and log in as `admin` / `admin`.
   6. Under **Admin → Connections**, add the connection the DAG's load step uses: Connection Id `csai380_mysql`, type **MySQL**, host `mysql.<your-namespace>.svc.cluster.local`, schema `csai380`, login `root`, port `3306`, and the password from your 2.4 secret (`kubectl get secret mysql-credentials -n <your-namespace> -o jsonpath='{.data.root-password}' | base64 -d`). Enter it in the UI only, never in a file you commit.
   7. Unpause `csai380_etl_pipeline`, trigger it, and confirm all three tasks succeed. Save a screenshot showing the successful task graph as `evidence/3.4-dag-success.png` in your repository, then embed or link it in `README.md`.

### Part Three: Modify the Transform Phase

6. The provided transform maps each user's phone country code to the ISO3166-1-Alpha-3 country code and official English country name. Extend it to also include **capital city, continent, currency name, and internet TLD**.

7. Re-run the DAG and query MySQL to confirm the new columns are populated. Record the before/after table schema and one sample row in your README.

8. Intentionally break the transform (e.g., reference a column that doesn't exist), re-run, and practice the troubleshooting workflow: **Observe → Diagnose → Remediate → Verify**. Document each of the four steps — which Airflow logs you read, what the error meant, what you changed, and how you verified the fix.

### Part Four: Reconfigure Airflow via Helm Values

9. Airflow in this course is installed with Helm. Its configuration lives in `helm/airflow-values.yaml` in your repository (provided as [starter/helm/airflow-values.yaml](starter/helm/airflow-values.yaml)) — that file is the source of truth, not the UI.

10. Make one configuration change through the values file (for example, change the DAG sync interval or add an environment variable), then apply it:

    ```bash
    helm upgrade airflow apache-airflow/airflow -n <your-namespace> -f helm/airflow-values.yaml
    ```

11. Verify the change took effect and note in your README why changing the values file beats changing settings in the UI.

### Part Five: Guard the DAG with CI

12. Add `.github/workflows/dag-lint.yml` to your repository (starting from [starter/.github/workflows/dag-lint.yml](starter/.github/workflows/dag-lint.yml)) with a job that runs on every pull request and:
    1. Lints your DAG files with `ruff` (or `flake8`).
    2. Runs `python -m py_compile` (or an `airflow dags list` import check) so a DAG with a syntax error cannot merge.

13. Open a pull request with all of the above, confirm the CI job passes, merge, and **submit** the link to your GitHub repository to Canvas.

### Park it, don't delete it

Airflow idles expensively — several pods doing nothing between DAG runs. When you finish, park the namespace (Deployments and StatefulSets) and keep the data:

```bash
kubectl scale deployment,statefulset --all --replicas=0 -n <your-namespace>
```

Airflow's metadata database keeps your DAG-run history on its PVC, and MySQL keeps your loaded rows. Scale back up to resume — no reinstall needed.

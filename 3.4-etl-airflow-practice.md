## Purpose:

This week's project installs Airflow and builds your pipeline; this exercise makes sure you actually understand the moving parts before you depend on them. Working inside a pre-configured Kubernetes application, you will implement an extraction phase, modify a transform phase to see its effect, and reconfigure Airflow through its Helm values — the IaC way, not by clicking.

You will also provision the object storage your pipeline reads from using Terraform, and add a CI check so a broken DAG never reaches your cluster.

## Instructions:

### Part One: Provision Object Storage with Terraform

1. On a new branch (`etl-practice`), add a Terraform resource to your `terraform/` directory that creates a **Google Cloud Storage bucket** for raw data (provided as [starter/terraform/gcs-bucket.tf](starter/terraform/gcs-bucket.tf)). Run `terraform plan` and `terraform apply`, and commit the configuration.

2. Upload the [country-codes CSV file](https://github.com/datasets/country-codes/blob/main/data/country-codes.csv) to your bucket using `gsutil cp` or the console. This is your extraction source.

### Part Two: Implement the Extraction Phase

3. Open the pre-configured ETL DAG provided at [starter/dags/etl_pipeline.py](starter/dags/etl_pipeline.py) and copy it into your repository's `dags/` directory. The transform and load phases are written; the **extract phase is a stub** marked `# TODO(student)`.

4. Implement the extract step as a Python Airflow task that:
   1. Reads the country-codes CSV from your GCS bucket.
   2. Reads simulated user signup events (JSON) from Redis (provided by the starter app).
   3. Passes both onward to the transform step.

5. Trigger the DAG from the Airflow UI and confirm the extract task succeeds. Screenshot the successful task graph for your README.

### Part Three: Modify the Transform Phase

6. The provided transform maps each user's phone country code to the ISO3166-1-Alpha-3 country code and official English country name. Extend it to also include **capital city, continent, currency name, and internet TLD**.

7. Re-run the DAG and query MySQL to confirm the new columns are populated. Record the before/after table schema and one sample row in your README.

8. Intentionally break the transform (e.g., reference a column that doesn't exist), re-run, and practice the troubleshooting workflow: **Observe → Diagnose → Remediate → Verify**. Document each of the four steps — which Airflow logs you read, what the error meant, what you changed, and how you verified the fix.

### Part Four: Reconfigure Airflow via Helm Values

9. Airflow in this course is installed with Helm. Its configuration lives in `helm/airflow-values.yaml` in your repository (provided as [starter/helm/airflow-values.yaml](starter/helm/airflow-values.yaml)) — that file is the source of truth, not the UI.

10. Make one configuration change through the values file (for example, change the DAG sync interval or add an environment variable), then apply it:

    ```bash
    helm upgrade airflow apache-airflow/airflow -n <your-namespace> -f helm/airflow-values.yaml
    ```

11. Verify the change took effect and note in your README why changing the values file beats changing settings in the UI.

### Part Five: Guard the DAG with CI

12. Add a job to your GitHub Actions workflow that runs on every pull request (provided as [starter/.github/workflows/dag-lint.yml](starter/.github/workflows/dag-lint.yml)) and:
    1. Lints your DAG files with `ruff` (or `flake8`).
    2. Runs `python -m py_compile` (or an `airflow dags list` import check) so a DAG with a syntax error cannot merge.

13. Open a pull request with all of the above, confirm the CI job passes, merge, and **submit** the link to your GitHub repository to Canvas.

Helm install, topic create on `kafka-controller-0`, console round trip (3/3), the STEDI simulator publishing risk events to the topic, the logging consumer receiving them, and the consumer-downtime experiment (lag built while down, drained after restart).
> **Starter files:** [starter/helm/kafka-values.yaml](starter/helm/kafka-values.yaml), [starter/k8s/kafka/logging-consumer.yaml](starter/k8s/kafka/logging-consumer.yaml), [starter/k8s/stedi-simulator.yaml](starter/k8s/stedi-simulator.yaml)

## Purpose:

Before you wire Kafka into your block project, you need to see one event travel the whole road: a producer writes it, a topic stores it, a consumer reads it. In this exercise you will deploy Kafka to Kubernetes with Helm, create a topic, and move messages through it — first by hand with the console scripts, then with a producer that sends real project data and a consumer/sink that receives it.

As always, the Helm values and manifests that define Kafka live in your GitHub repository and deploy through your pipeline, not from your laptop's command history.

- **(b) Build infrastructure that AI operations run on.** Event streams are the nervous system of production AI: user events feed real-time features for online inference, prediction requests and results flow through topics for monitoring and retraining, and model telemetry is streamed for drift detection.

## Instructions:

> **If you parked earlier weeks:** this exercise uses your application from 1.4 as the producer — un-park it with `kubectl scale deployment <your-app> --replicas=1 -n <your-namespace>`. Redis, MySQL, and Airflow can stay parked.

### Part One: Deploy Kafka with Helm

1. On a new branch (`kafka-practice`), add a `helm/kafka-values.yaml` file to your repository (provided as [starter/helm/kafka-values.yaml](starter/helm/kafka-values.yaml)). Keep it small: one broker is plenty for this exercise (another "never in production" moment — note why in your README).

2. Install Kafka into your namespace:

   ```bash
   helm repo add bitnami https://charts.bitnami.com/bitnami
   helm install kafka bitnami/kafka -n <your-namespace> -f helm/kafka-values.yaml
   ```

3. Verify the broker is running with `kubectl get pods -n <your-namespace>` and inspect its logs. Record in your README how you knew the broker was healthy.

### Part Two: Create a Topic and Move Messages by Hand

4. Create at least one topic (for example, `practice-events`):

   ```bash
   kubectl exec -it kafka-controller-0 -n <your-namespace> -- \
     kafka-topics.sh --create --topic practice-events \
     --bootstrap-server localhost:9092 --partitions 3 --replication-factor 1
   ```

5. In one terminal, start a console producer against the topic using `kafka-console-producer.sh` and type several test messages.

6. In a second terminal, start `kafka-console-consumer.sh` with `--from-beginning` and confirm every message arrives. Capture both terminals side by side in `evidence/4.4-console-round-trip.png` and embed or link the screenshot in `README.md`.

7. Answer in your README: what do **partitions** do, and what happens to message ordering across them?

### Part Three: A Real Producer and a Real Consumer

8. Configure a **producer/source** that sends project data into Kafka: the **STEDI simulator**. It creates test customers, records a balance test every 2 seconds, and publishes each customer's fall-risk score to Kafka. The [Simulator (demo data)](https://github.com/STEDI-Balance/stedi-web#simulator-demo-data) section of the stedi-web README explains the settings and shows what an event looks like.
   1. In your `k8s/stedi-simulator.yaml` from 3.4 (or a fresh copy of [starter/k8s/stedi-simulator.yaml](starter/k8s/stedi-simulator.yaml) with `<stedi-image>` replaced), uncomment `KAFKA_BROKER` and `KAFKA_STEDI_EVENTS_TOPIC`, and set them to your broker (`kafka.<your-namespace>.svc.cluster.local:9092`) and the topic you created in step 4.
   2. Commit the manifest change and apply it. Within a minute, `kubectl logs deploy/stedi-simulator -c stedi -n <your-namespace>` shows `Sending to Kafka Topic: <your-topic>`, and the console consumer from step 6 shows risk events such as `{"customer":"Sarah.Jones.0@test.com","score":-16.0,...}`.

9. Configure a **consumer/sink** that receives the events: copy [starter/k8s/kafka/logging-consumer.yaml](starter/k8s/kafka/logging-consumer.yaml) into your repository as `k8s/kafka/logging-consumer.yaml` and deploy it so each event is written to its pod logs. Verify with `kubectl logs` that events produced by the application appear in the consumer.

10. Stop the consumer, keep producing for a minute, then start the consumer again. In your README, explain what happened to the messages produced while the consumer was down, and why.

### Part Four: Classify the Processing Model

11. In your README, state whether this producer → topic → consumer flow is **batch, micro-batch, or streaming**, and defend your answer in 4–5 sentences using this week's readings.

12. Open a pull request, confirm CI passes, merge, and **submit** the link to your GitHub repository to Canvas.

### Park it, don't delete it

When you finish, park the namespace — compute to zero, state kept:

```bash
kubectl scale deployment,statefulset --all --replicas=0 -n <your-namespace>
```

Your topic and its messages live on Kafka's PVC, so they survive parking — and 5.4 picks up exactly this stack. Scale `kafka-controller`, your producer, and the consumer back to 1 next week and the events are still there.

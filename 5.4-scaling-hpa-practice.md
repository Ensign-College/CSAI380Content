> **Starter files:** [starter/k8s/hpa.yaml](starter/k8s/hpa.yaml), [starter/scripts/load-generator.sh](starter/scripts/load-generator.sh)

## Purpose:

"Just add replicas" is the most common — and most commonly wrong — answer in operations. This exercise teaches you to scale like an engineer: take a baseline measurement, change capacity through code review (GitOps-style, via pull request), and measure again so you can prove what the change actually did.

You will scale a Kafka consumer group, watch consumer lag grow and shrink, and configure a Horizontal Pod Autoscaler (HPA) so Kubernetes does the scaling for you.

- **(b) Build infrastructure that AI operations run on.** Scaling is the economics of AI: inference traffic spikes demand autoscaled serving capacity (and idle GPUs burn money), consumer groups parallelize feature and embedding pipelines, and lag is the early-warning signal that your AI system is falling behind reality.

## Instructions:

> **If you parked week 4:** un-park the Kafka stack first — `kubectl scale statefulset kafka-controller --replicas=1 -n <your-namespace>` and `kubectl scale deployment <your-producer> <your-consumer> --replicas=1 -n <your-namespace>`. Your topic and its messages are still on Kafka's PVC.

### Part One: Establish the Baseline

1. On a new branch (`scaling-practice`), ensure your producer (from 4.4) is generating a steady stream of events, and your consumer deployment is running with **1 replica**.

2. Measure the baseline. Use the consumer-group tool to observe lag:

   ```bash
   kubectl exec -it kafka-0 -n <your-namespace> -- \
     kafka-consumer-groups.sh --bootstrap-server localhost:9092 \
     --describe --group <your-consumer-group>
   ```

3. Record in `SCALING.md`: current lag per partition, number of consumers, and which consumer owns which partition.

### Part Two: Break It, Then Watch

4. Stop the consumer (`kubectl scale deployment <consumer> --replicas=0 -n <your-namespace>`) while the producer keeps running for ~2 minutes.

5. Re-run the consumer-groups command every 30 seconds and record the lag numbers. In `SCALING.md`, describe what you observed and what this means for a real system whose consumer crashes on a Friday night.

### Part Three: Scale Through a Pull Request

6. Restart the consumer at 1 replica and watch it catch up. Record how long recovery took.

7. Now scale the proper way: edit the `replicas` field in your consumer's deployment manifest **in Git**, open a pull request, merge it, and let your GitHub Actions pipeline apply the change. Scale to **3 replicas**.

8. Re-run the consumer-groups command. In `SCALING.md`, record: how the partitions were redistributed across consumers, and how lag behavior compares to the 1-replica baseline.

9. Answer in `SCALING.md`: your topic has 3 partitions. What would happen if you scaled to **5** consumer replicas? Why? (Verify your answer experimentally if you want the fun version.)

### Part Four: Let Kubernetes Do It — HPA

10. Add an `k8s/hpa.yaml` manifest (provided as [starter/k8s/hpa.yaml](starter/k8s/hpa.yaml)) that configures a **HorizontalPodAutoscaler** for a processing component (CPU-based, min 1, max 4). Commit it and deploy via your pipeline.

11. Generate load (increase the producer's event rate or use the provided [starter/scripts/load-generator.sh](starter/scripts/load-generator.sh)) and watch the HPA act:

    ```bash
    kubectl get hpa -n <your-namespace> --watch
    ```

12. In `SCALING.md`, record the scale-up event, the metrics that triggered it, and what happened when load stopped. Then answer: **why does increased capacity here create increased responsibility elsewhere in the system?** (Hint: what did your MySQL sink feel when consumers tripled?)

13. Merge your branch and **submit** the link to your GitHub repository to Canvas.

### Park it, don't delete it

One wrinkle this week: an HPA immediately scales its target back up to `minReplicas`, so remove the HPA object first (its manifest is safe in Git):

```bash
kubectl delete -f k8s/hpa.yaml -n <your-namespace>
kubectl scale deployment,statefulset --all --replicas=0 -n <your-namespace>
```

Everything stateful stays on its PVCs. This ends the skill-practice sequence — leave the namespace parked and re-apply from Git whenever you need it: nothing has to be rebuilt from scratch.

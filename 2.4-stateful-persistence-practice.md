## Purpose:

Last week you deployed stateless workloads — when a pod died, nothing of value was lost. This week your project gains memory. This assignment walks you through the single most important experiment in stateful Kubernetes: **deploy a database, insert data, delete the pod, and see what happens** — first without persistent storage, then with it.

Along the way you will practice PersistentVolumes, PersistentVolumeClaims, StorageClasses, and StatefulSets, and you will keep every manifest in GitHub so your infrastructure stays reviewable and reproducible.

Record the goal, the commands the agent chose, and whether its explanation of the result matched what you later wrote yourself.
- **(b) Build infrastructure that AI operations run on.** Persistent storage is where AI state lives: training checkpoints that must survive preempted GPU pods, feature stores and vector databases backing inference, and datasets staged for training.

## Instructions:

### Part One: Prepare

1. Create a branch named `stateful-practice` in your course repository. All manifests for this exercise go in `k8s/stateful/`. Open a pull request when you are done so your work is reviewable — merging to `main` deploys via your GitHub Actions workflow from Week 1.

2. Use your AI tutor project to review: StatefulSet vs. Deployment, PV, PVC, StorageClass, and access modes. Copy the provided [starter/k8s/stateful/NOTES.md](starter/k8s/stateful/NOTES.md) template into `k8s/stateful/NOTES.md` and write a one-paragraph summary of each — in your own words.

### Part Two: Round One — A Database with Amnesia

3. Create a **Redis Deployment** (yes, a Deployment — on purpose) and a **headless Service** for it in your namespace, starting from [starter/k8s/stateful/redis-deployment.yaml](starter/k8s/stateful/redis-deployment.yaml) and [starter/k8s/stateful/redis-headless-service.yaml](starter/k8s/stateful/redis-headless-service.yaml). Do **not** attach any persistent storage yet.

4. Connect to Redis and insert data:

   ```bash
   kubectl exec -it <redis-pod> -n <your-namespace> -- redis-cli
   SET student:name "<your name>"
   SET course "CSAI 380"
   KEYS *
   ```

5. Now delete the pod:

   ```bash
   kubectl delete pod <redis-pod> -n <your-namespace>
   ```

6. Wait for the replacement pod, reconnect with `redis-cli`, and run `KEYS *` again.
   1. In `k8s/stateful/NOTES.md`, record the insert, pod deletion, and before/after `KEYS *` commands and their relevant output. Answer: **What happened to your data, and why?**

### Part Three: Round Two — Storage That Survives

7. Create a **PersistentVolumeClaim** (`k8s/stateful/mysql-pvc.yaml`, provided as [starter/k8s/stateful/mysql-pvc.yaml](starter/k8s/stateful/mysql-pvc.yaml)) using the cluster's default StorageClass. Inspect it:

   ```bash
   kubectl get pvc -n <your-namespace>
   kubectl get storageclass
   ```

   1. In `k8s/stateful/NOTES.md`, record which StorageClass was used, the access mode, and what that access mode implies.

8. Create a **MySQL Deployment** that mounts the PVC at `/var/lib/mysql`, starting from [starter/k8s/stateful/mysql-deployment.yaml](starter/k8s/stateful/mysql-deployment.yaml).
   1. The MySQL root password must come from a **Kubernetes Secret**, not plain text in the manifest. Create the Secret with `kubectl create secret` and reference it with `secretKeyRef`.
   2. In `k8s/stateful/NOTES.md`, record the Secret's name and how you verified it exists; do not record its password or other secret values.
   3. Disclaimer: a single-node MySQL is not production-grade — production wants high availability and clustering via Helm charts, which we cover later.

9. Repeat the experiment: connect with the MySQL client, create a table, insert a row, delete the pod, wait for the replacement, and query the table again.
   1. In `k8s/stateful/NOTES.md`, record the relevant create/insert, pod deletion, and post-restart query commands and output. Answer: **What happened this time, and exactly which Kubernetes objects made the difference?**

### Part Four: Compare and Conclude

10. In `k8s/stateful/NOTES.md`, write a short comparison (4–6 sentences): when should you reach for a StatefulSet instead of a Deployment with a PVC? Reference what you observed in both rounds.

11. Merge your pull request, confirm the Actions run is green, and **submit** the link to your GitHub repository (with the merged PR visible) to Canvas.

### Park it, don't delete it

You just proved that data on a PVC outlives its pod. The same idea covers whole weeks: when you finish, scale compute to zero and keep the volumes — real operators park idle environments, they don't drop the database:

```bash
kubectl scale deployment --all --replicas=0 -n <your-namespace>
```

The PVC — and every MySQL row on it — stays, and week 3's ETL exercise reads this same database. Scale back to 1 when you need it. Never delete a PVC unless you intend to destroy its data.

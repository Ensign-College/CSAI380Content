## Purpose:

This assignment gives you hands-on experience taking an application from a Docker image to a working Kubernetes deployment on Google Kubernetes Engine (GKE). You will practice building, running, pushing, and pulling Docker images; creating Kubernetes deployments and services; and using commands to inspect and troubleshoot your work.

You will also establish the infrastructure-as-code (IaC) habits you will use for the rest of the course: everything you deploy is described in files, those files live in GitHub, and a GitHub Actions pipeline builds and publishes your container image automatically. Finally, you will use AI to strengthen your understanding by creating a Mermaid diagram and writing Markdown as you document what you learn.

## AI Ops in This Assignment:

This course is about **AI Ops in both senses**, and every assignment asks you to practice both. Add an **AI Ops reflection** section to your README covering each:

- **(a) Use an agent to do the ops.** Give your coding agent a goal such as "the hello-app Deployment is Running in my namespace and the Service answers an in-cluster curl," and let it write the manifests and iterate with `kubectl get/describe/logs` until the goal is met. Record: the goal you gave it, how the agent knew the goal was achieved, and at least one thing it got wrong that you had to catch (connect this to the Agent Loops reading in Part One).
- **(b) Build infrastructure that AI operations run on.** Containers, registries, Deployments, and Services are exactly how AI systems ship: a model server is a container image in a registry, served by a Deployment behind a Service, and namespaces isolate training from serving.

## Instructions:

### Part One: Set Up Your Tools and Repository

1. If you haven't already, install VS Code (or Codex) and the following command-line tools:
   1. `git`
   2. `docker`
   3. `kubectl`
   4. `gcloud` (Google Cloud CLI)
   5. `terraform`

2. Use AI or a search engine to study **Agent Loops**, and how goals factor into Agent Loops.
   1. As you work through the following steps, keep two questions in mind: "What goal have I defined for my agent?" and "How will it know when it has completed the goal?"

3. Go to the Canvas assignment and accept the GitHub repository:
   1. Open the repository in VS Code or Codex. **All files you create in this exercise belong in this repository.** If it isn't in Git, it didn't happen.

4. Log in to your Vocareum-provided GCP environment and create your own GKE Autopilot cluster. You will use this cluster for the rest of the course, including the Block Project. Creating it takes about 5–10 minutes:

   ```bash
   gcloud services enable container.googleapis.com
   gcloud container clusters create-auto <cluster-name> --region us-east1
   gcloud container clusters get-credentials <cluster-name> --region us-east1
   kubectl get nodes
   ```

   Autopilot adds nodes only when pods need them, so `kubectl get nodes` may list few or no nodes until you deploy something.

### Part Two: Provision Your Workspace with Terraform

5. In your repository, create a `terraform/` directory. Starting from the provided [starter/terraform/main.tf](starter/terraform/main.tf) and [starter/terraform/variables.tf](starter/terraform/variables.tf), write Terraform that provisions:
   1. A Kubernetes **namespace** named with your GitHub username (this is your personal sandbox for the semester).
   2. A **Google Artifact Registry** Docker repository to hold your images.

6. Run the standard Terraform workflow and read the output of each step:

   ```bash
   terraform init
   terraform plan
   terraform apply
   ```

7. Commit the `terraform/` directory (never commit `.tfstate` files — the starter `.gitignore` handles this).

### Part Three: Deploy a Pre-Made Image

8. Deploy a pod to Kubernetes using the **busybox** image (BusyBox is a tiny Linux container image — perfect for exploring).
   1. Write a pod manifest in `k8s/busybox-pod.yaml` and apply it to your namespace.
   2. Practice the three essential inspection commands and record what each tells you:

      ```bash
      kubectl get pods -n <your-namespace>
      kubectl describe pod busybox -n <your-namespace>
      kubectl logs busybox -n <your-namespace>
      ```

### Part Four: The Docker Image Lifecycle

9. Learn how to do each of the following, and document each step with the command you used and a screenshot or terminal output in your README (start from the provided [starter/Dockerfile](starter/Dockerfile) and [starter/app/server.py](starter/app/server.py)):
   1. Pull and run a Docker image from the Docker Hub registry.
   2. Write a `Dockerfile` for a simple application (a one-line Dockerfile is a fine start).
   3. Build a Docker image from your Dockerfile.
   4. Run your local image.
   5. Push your Docker image to your Artifact Registry repository.
   6. Pull it back from the registry.
   7. Deploy your application to Kubernetes using your pushed image.
   8. **Apple Silicon (M-series) Macs:** GKE nodes are `amd64`, so build the image you push with `docker build --platform linux/amd64 ...` — otherwise your pods will crash with `exec format error`.

### Part Five: Automate the Build with GitHub Actions

10. Create a workflow at `.github/workflows/build-and-push.yml` (starting from [starter/.github/workflows/build-and-push.yml](starter/.github/workflows/build-and-push.yml)) that:
    1. Triggers on every push to `main`.
    2. Builds your Docker image.
    3. Pushes the image to your Artifact Registry repository.
    4. Authenticates to GCP with a service-account key stored as a **GitHub Actions secret** named `GCP_SA_KEY` — never hard-code credentials in the workflow file. Create the service account, key, and secret in the next step.

11. Create a CI service account for GitHub Actions and store its key as a repository secret. Run these with the gcloud CLI, logged in to your Vocareum-provided project:

    ```bash
    PROJECT_ID=$(gcloud config get-value project)
    SA=github-actions@$PROJECT_ID.iam.gserviceaccount.com

    # 1. A service account that only your pipeline uses
    gcloud iam service-accounts create github-actions --display-name="GitHub Actions CI"

    # 2. Allow it to push images to Artifact Registry
    gcloud projects add-iam-policy-binding $PROJECT_ID \
      --member="serviceAccount:$SA" --role=roles/artifactregistry.writer --condition=None

    # 3. Create a JSON key OUTSIDE your repository so it can never be committed
    mkdir -p ~/.csai380
    gcloud iam service-accounts keys create ~/.csai380/github-actions-key.json --iam-account=$SA
    ```

    Add the key to your repository as a secret named `GCP_SA_KEY`, either with the [GitHub CLI](https://cli.github.com/) from inside your repository:

    ```bash
    gh secret set GCP_SA_KEY < ~/.csai380/github-actions-key.json
    gh secret list    # GCP_SA_KEY appears; its value is never shown
    ```

    or in the GitHub web UI: **Settings → Secrets and variables → Actions → New repository secret**, name `GCP_SA_KEY`, and paste the entire contents of the key file.

    Keep `~/.csai380/github-actions-key.json`: you will add the same key to your Block Project repository in 1.5. Treat it like a password — never commit it, paste it into chat, or share it. If it is ever exposed, delete it with `gcloud iam service-accounts keys delete <key-id> --iam-account=$SA` and create a new one.

12. Push a small change and confirm the workflow runs green in the Actions tab. Include a link to a successful run in your README.

### Part Six: Deployments and Services

13. Create a **Deployment** manifest (`k8s/deployment.yaml`) that uses your Docker image from Artifact Registry, and a **Service** manifest (`k8s/service.yaml`) that exposes your deployment.
    1. Apply both, then verify with `kubectl get deployments,services,pods -n <your-namespace>`.
    2. Delete one pod and watch the Deployment replace it. Note what happened in your README.

### Part Seven: Document with AI

14. Prompt your coding agent to make a **Mermaid diagram** of how to make a peanut butter and jelly sandwich in a file called `PBJ.md`. Verify the diagram renders in your repository on GitHub.

15. Learn about Markdown using AI as your teacher. Apply what you learn: your repository `README.md` must include headings, a table of the commands you learned, at least one code block, and links to your workflow run.

16. **Submit** the link to your GitHub repository to Canvas.

### Park it, don't delete it

In real operations you rarely tear down what you built — you scale idle compute to zero and keep the state. When you finish this exercise, park your namespace instead of deleting anything:

```bash
kubectl scale deployment --all --replicas=0 -n <your-namespace>
```

Your manifests stay in Git, your image stays in Artifact Registry, and your namespace keeps its configuration. Next week `kubectl scale deployment <name> --replicas=1` (or a pipeline run) brings it all back — nothing has to be rebuilt.
